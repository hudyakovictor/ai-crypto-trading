# Аудит кода: 200 находок и план кратного повышения потенциала

Дата: 2026-10-19. Ветка: `arena/4f0c63bc-ai-crypto-trading`. Коммит базы: `15f2df8`.
Объём кода: ~15 200 строк, 73 файла. `tsc --noEmit` — 0 ошибок. `eslint .` — 7 ошибок.

## Цель системы (как её сформулировал заказчик)

Полностью автономный цикл: раз в 15 минут получить свежие котировки → записать прогноз в БД
→ через 15 минут проверить котировки и записать «прогноз прошёл / не прошёл» → обучиться на
накопленных данных → ИИ сам генерирует гипотезы и сам их тестирует. Бесконечный цикл без
человека и без биржевых заявок.

## Как проводился аудит

1. Прочитан каждый файл репозитория (все 73).
2. Движок запущен вне БД на синтетических, но реалистичных 15-минутных сериях
   (волатильность 8–90% годовых, 300–400 состояний) — проверялись распределение режимов,
   дисперсия каждой из 15 категорий, распределение EVS, детерминизм связок, поведение
   outcome-evaluator и планировщика. Результаты — в приложении А.
3. Все утверждения ниже привязаны к файлу и строке. Там, где есть замер, он приведён.

## Легенда

- 🔴 **КРИТ** — ломает корректность выводов системы или её автономность. Чинить в первую очередь.
- 🟠 **ВЫСОКИЙ** — сильно снижает потенциал/надёжность, но не делает выводы ложными сразу.
- 🟡 **СРЕДНИЙ** — технический долг, производительность, честность UI.
- 🔵 **ИДЕЯ** — не ошибка, а способ кратно поднять потенциал.

## 10 главных проблем (если читать только это)

1. **Цикл не автономен.** Его запускает открытая вкладка браузера (`app-shell.tsx:266-286`) и
   `ensureAutopilot()`, который стартует только когда кто-то дёрнул `/api/research/status`.
   Нет `instrumentation.ts`, нет worker-процесса, нет cron. Закрыл ноутбук — лаборатория встала.
2. **Метки исходов считаются с утечкой во времени.** `outcome-evaluator.ts:45` включает в окно
   свечи за 15 минут ДО фиксации прогноза и не имеет верхней границы по `resolveAt`.
   Замер: свеча со скачком до фиксации дала MFE = 900%; свеча через 1.75 ч после горизонта — MFE = 3%.
3. **Обучение переобучается на собственной истории.** `autopilot.ts:66-88` после каждого цикла
   прогоняет ВСЕ resolved-прогнозы через инкрементный `updateFromOutcomes` → счётчики выборок
   растут квадратично, байесовский приор обесценивается, свежие данные тонут в пересчитанном прошлом.
4. **Brier измеряет не калибровку.** `learning-loop.ts:118` берёт в качестве «предсказанной
   вероятности» апостериорный win-rate той же категории по тем же данным. Метрика само-ссылочна
   и всегда выглядит хорошо. Настоящая вероятность (`1 − uncertainty` гипотезы) не используется.
5. **«15 независимых категорий» — это ~5 источников информации.** Замер корреляций:
   `derivatives_positioning` ≡ `cross_exchange_dispersion` (r = 1.00), `volume_liquidity` ≡
   `stablecoin_flow_proxies` (0.97), `price_returns` ≡ `cross_asset_relationships` (0.997),
   `on_chain_activity` — константа (sd = 0). Cross-agreement измеряет избыточность, а не конфлюэнс.
6. **Знак и направление фандинга противоречат друг другу.** `feature-engine.ts:336-341`:
   при funding = +0.0005 `normalizedScore = +1.000`, а `direction = DOWN`. Композит и UI говорят
   противоположное.
7. **Режим рынка определяется неверно почти всегда.** `feature-engine.ts:148-155`: волатильность
   считается по ПЕРВЫМ 30 барам, пороги годовой волатильности 0.08/0.02 недостижимы.
   Замер: на 400 реалистичных сериях `RANGING` не получен ни разу; на тихом рынке (8–12% годовых)
   71% серий помечены `VOLATILE`.
8. **Параметр `lookback` — декорация.** Он не участвует в вычислении связки, но входит в подпись
   стратегии → одна и та же стратегия размывается по 4 подписям, история никогда не набирает n.
   Замер: 81 уникальное поведение на 100 связок.
9. **Фабрикация помечается как живые данные.** `okx-client.ts:253` в catch возвращает синтетический
   OI с `isLive: true`; `autonomous-scheduler.ts:190-212` пишет синтетические свечи в БД с
   `confirmed: true`; `/api/research/seed` при первом открытии страницы заливает выдуманные исходы
   и обучает на них веса.
10. **Статистика имитируется, а не считается.** `walkforward/route.ts:59-84,106`: бенчмарки
    (48.2%, 52.1%, 53.4%) и вердикт аудита утечек «PASSED» — захардкоженные строки. Собственный
    протокол в `research/README.md` это прямо запрещает. Плюс нет ни одной поправки на множественные
    сравнения при переборе 100 связок × N активов каждый цикл.

# A. Автономность и оркестрация цикла (1–20)

**1. 🔴 Цикл запускается из браузера.** `src/components/app-shell.tsx:266-286` — клиентский
`setInterval` считает countdown и на нуле вызывает `POST /api/research/cycle`. Нет вкладки — нет
цикла. Это прямое противоречие цели «максимально автономно».
→ Триггер должен жить на сервере и быть единственным.

**2. 🔴 Серверный автопилот не стартует сам.** `src/lib/quant/autopilot.ts:91-100` —
`ensureAutopilot()` вызывается только из `getAutopilotState()`/`setAutopilotEnabled()`, то есть из
API-роутов. В Next.js нет `instrumentation.ts`, поэтому после рестарта сервер без единого
внешнего запроса цикл не запустит никогда.
→ Добавить `src/instrumentation.ts` с `register()`, который вызывает `ensureAutopilot()`.

**3. 🔴 `timer.unref()` убивает цикл в serverless.** `autopilot.ts:96`. На Vercel/Lambda/Cloud Run
инстанс засыпает между запросами, интервал не срабатывает. `unref()` к тому же не даёт процессу
«держать» таймер — при `next start` без нагрузки цикл может не пережить graceful shutdown.
→ Для прода: внешний планировщик (cron/worker-контейнер), а не интервал в веб-процессе.

**4. 🟠 Два независимых триггера конфликтуют.** Серверный tick каждые 60 с с порогом 14 минут
(`autopilot.ts:50`) и клиентский countdown 15 минут (`app-shell.tsx:278`). Оба могут запустить цикл
в одном окне; клиентский помечает его `manual_trigger_15m`, и статистика «ручных» циклов загрязняется.

**5. 🟠 Рассинхрон интервалов: 14 vs 15 минут.** `autopilot.ts:50` — 14 минут,
`scheduler.intervalMinutes` — 15, UI показывает 15. Горизонт прогноза 15 минут, значит разрешение
случайно попадает либо ровно в срок, либо через 29 минут (см. находку 103).

**6. 🔴 Нет идемпотентности по временному бакету.** Цикл не привязан к границе 15-минутной свечи
UTC. Рестарт после сбоя запускает второй цикл в том же бакете и создаёт дубли гипотез.
→ Ключ цикла = `floor(now / 900000)`, unique-индекс в таблице `cycle_runs`.

**7. 🔴 Блокировка только внутри процесса.** `isRunning` — поле экземпляра синглтона
(`autonomous-scheduler.ts:64,102`). Две реплики приложения = два параллельных цикла, дубли forecasts,
гонки в `learning_weights`.
→ `pg_advisory_xact_lock` или строка-замок в БД с heartbeat.

**8. 🟠 Критическое состояние живёт в памяти.** `cycleIndex`, `lastUniverse`, `lastPlannerDecision`
(`autonomous-scheduler.ts:66-72`), `streaks` (`universe.ts:287`), `scanCache` (`universe-store.ts:27`).
После рестарта exploration-ротация и anti-crowding обнуляются, состав вселенной «забывается».

**9. 🟠 Счётчики автопилота не переживают HMR/рестарт.** `cyclesCompleted`, `retrainsCompleted` —
в `globalThis` (`autopilot.ts:27-43`). UI показывает «0 циклов» при живой истории в БД.

**10. 🔴 Нет транзакции на цикл.** ~10 этапов пишут в 8 таблиц последовательно
(`autonomous-scheduler.ts:118-660`). Падение на шаге 9 оставляет сигналы и комбинации без гипотез,
а гипотезу — без прогноза (вставка двумя отдельными запросами, строки 520 и 545).

**11. 🔴 Ошибка внутри цикла не локализована.** `runCycle` имеет `try/finally`, но не `catch` на
отдельные шаги и не `try` на каждый pick. Unique-конфликт `hypotheses.code` (см. 114) роняет весь
цикл после частичных записей.

**12. 🟠 Разрешение прогнозов заложено в цикл генерации.** Если OKX недоступен, `scanUniverse`
возвращает синтетику, и уже созревшие прогнозы либо разрешаются по выдуманным ценам, либо не
разрешаются вовсе. Разрешение должно работать от сохранённой истории свечей, независимо от скана.

**13. 🔴 Прогнозы «выпавших» активов разрешаются выборочно.** `autonomous-scheduler.ts:135-142`:
для активов вне вселенной добираются свечи, но `.slice(0, 12)` — если таких активов больше 12,
остальные прогнозы зависают в `pending` навсегда.

**14. 🔴 Статус `expired` никогда не выставляется.** Он есть в схеме (`forecasts.status`,
`outcome`) и в типах (`types.ts:34-35`), но ни одна ветка кода его не присваивает. Просроченный
прогноз молча висит или разрешается с опозданием в 30–60 минут.

**15. 🟡 Нет ретраев и backoff.** `fetchWithTimeout` (`okx-client.ts:29-46`) — одна попытка,
5 секунд. 429/503 от OKX сразу роняет запрос в синтетику. Нет jitter, нет повторной попытки,
нет учёта `Retry-After`.

**16. 🟡 Нет глобального rate-limiter'а на OKX.** Цикл: 1 tickers + 32 candles + 10×(book+funding+oi)
≈ 63 запроса. Плюс `/heatmap` (каждые 90 с, ~30 запросов) и `/combinations` (~5 запросов) из UI.
Публичные лимиты OKX — 20–40 req/2s на эндпоинт с IP-баном при превышении. `mapLimited(4)` —
единственная защита.

**17. 🟡 Всё в одном HTTP-запросе.** `/api/research/cycle` с `maxDuration = 75`. На serverless это
ограничение платформы; на любом хостинге длинный запрос держит соединение и падает по таймауту
прокси. Цикл должен быть фоновой задачей с очередью.

**18. 🔵 ИДЕЯ: три процесса вместо одного.** `worker` (цикл по расписанию, pg-lock),
`api` (только чтение/мутации UI), `backfill` (дозагрузка истории). Тогда веб-нагрузка никогда не
сорвёт эксперимент, а worker можно масштабировать/рестартовать независимо.

**19. 🔵 ИДЕЯ: планировщик по бакетам UTC.** Таблица `cycle_buckets(bucket bigint primary key,
started_at, finished_at, status, error)` с unique-ключом. Пропущенный бакет догоняется при старте
(`catch-up`), дубль невозможен физически.

**20. 🔵 ИДЕЯ: watchdog и алерты.** Отдельный таймер: если `last_cycle_at` старше 2× интервала,
если доля `isLive=false` за сутки выше порога, если hit-rate скользящего окна обрушился — писать
`ALERT` и слать уведомление (Telegram/webhook/e-mail). Автономность без эскалации = молчаливая поломка.

# B. Данные с биржи и целостность датасета (21–43)

**21. 🔴 Синтетический OI помечен как живой.** `okx-client.ts:244-255`: в `catch` возвращаются
хардкод-значения `oi: 12500, oiCcy: 850000000` и **`isLive: true`**. Это ровно тот класс бага,
который комментарии файла объявляют устранённым. Фабрикация уходит в сигнал с confidence 0.95.

**22. 🔴 Синтетические свечи пишутся в БД как подтверждённые.** `autonomous-scheduler.ts:190-212` —
цикл вставки не проверяет `member.dataLive`/`bundle.isLive` и ставит `confirmed: true`.
При outage OKX в `candles` навсегда оседают цены из `getBasePrice()` (BTC = 78000).

**23. 🔴 Реестр активов отравляется синтетикой.** Там же, строки 145-186: `lastPrice`,
`high24h`, `low24h`, `volume24h` обновляются из `tickers`, которые при падении OKX синтетические.
UI и ИИ-контекст потом читают эти числа как рыночные.

**24. 🟠 Синтетика недетерминирована.** `generateSyntheticTicker/Candles/OrderBook` используют
`Math.random()` (`okx-client.ts:277-345`), хотя секция озаглавлена «Realistic **Deterministic**
Synthetic Fallback». Два запуска дают разные данные → невозможно воспроизвести инцидент.

**25. 🟠 Off-by-one в генераторе свечей.** `okx-client.ts:304`: `for (let i = count; i >= 0; i--)`
возвращает `count + 1` свечей. Все окна (`slice(-20)`, `slice(-30)`) тихо смещаются.

**26. 🟠 Хардкод базовых цен устаревает.** `getBasePrice` (`okx-client.ts:263-275`): BTC 78000,
ETH 2450, SOL 145, XRP 2.15. Через месяц это другой рынок; система «видит» его при каждом сбое.
→ Синтетика должна либо отсутствовать, либо строиться от последней реальной цены в БД.

**27. 🔴 Не используется флаг `confirm` из ответа OKX.** `/api/v5/market/candles` возвращает 9 полей,
последнее — признак закрытия свечи. `okx-client.ts:121-131` читает только 7. Значит `candles[last]` —
это НЕЗАКРЫТАЯ свеча, и по ней считаются momentum, RVOL, order flow, liquidations, anomaly
(см. 47, 55, 62). Все эти значения систематически смещены к началу бара.

**28. 🔴 `fixedAt` не выровнен по границе свечи.** `hypothesis-engine.ts:141`: `fixedAt = new Date()`.
Цикл стартует в произвольную секунду → окно прогноза [t, t+15min] пересекает две свечи, и «прогноз
на 15 минут» фактически покрывает от 1 до 2 баров. Метка шумная и несопоставима между циклами.

**29. 🟠 История не накапливается.** Сохраняются только 3 последние свечи на участника вселенной
(`autonomous-scheduler.ts:191`). За месяц это ~2880 свечей на актив, и только для тех активов,
которые были в составе. `/market/history-candles` (до 100 баров на запрос, пагинация по `after/before`)
не используется вообще. **У системы нет датасета, на котором можно обучаться** — а это половина цели.

**30. 🟠 Дедупликация свечей — SELECT-then-INSERT.** Строки 192-197: на каждую свечу отдельный
запрос, уникальности на уровне БД нет (в схеме `candles` нет unique-индекса на
`(symbol, timeframe, timestamp)`). При двух параллельных циклах будут дубли.

**31. 🟠 Стакан, фандинг и OI не сохраняются.** Категории 5, 6, 7 считаются из мгновенного снапшота
и исчезают. Воспроизвести сигнал задним числом невозможно; бэктест по этим категориям невозможен
в принципе.

**32. 🟡 `parseFloat(x) || 0.0001` искажает нули.** `okx-client.ts:197,199`: реальный фандинг 0
(бывает на спокойном рынке) превращается в 0.0001. То же с `oi || 10000`, `oiCcy || 750000000`
(строки 236-237) — выдуманные «нейтральные» значения вместо честного `null`.

**33. 🟡 Нет валидации ответа OKX.** `parseInt(item.ts, 10)`, `parseFloat(row[1])` без radix/схемы.
Изменение формата ответа биржи даст молчаливые NaN → `clip()` превратит их в 0 (`feature-engine.ts:36`).
→ zod-схема на каждый эндпоинт.

**34. 🟡 Гэпы в свечах не детектируются.** Ни одна проверка не сравнивает соседние `timestamp` с
ожидаемым шагом 900000 мс. Пропуск бара silently меняет все окна. `errorType: "data_gap"` из-за
этого никогда не выставляется (см. 110).

**35. 🟡 Латентность измеряется неверно.** `okx-client.ts:60,112` — `latencyMs` фиксируется до
`await res.json()`. Тело ответа (сотни КБ для `/market/tickers`) парсится вне замера, поэтому
метрика качества данных занижена в разы.

**36. 🟡 Один базовый хост OKX.** `OKX_BASE_URL = "https://www.okx.com"` (`okx-client.ts:20`).
Нет запасного (`aws.okx.com`), нет учёта гео-ограничений, нет переключения при 403/451.

**37. 🟡 Кэш вселенной живёт 90 секунд в памяти.** `universe-store.ts:29,70-76`. При холодном
старте каждый запрос `/status` может запустить полный скан рынка (и имеет побочный эффект —
см. 88).

**38. 🔵 ИДЕЯ: `/api/v5/market/trades` для настоящего order flow.** Публичный эндпоинт отдаёт
последние сделки с полем `side` → реальный CVD, taker buy/sell imbalance, распределение размеров
сделок. Это заменяет прокси `(close − low)/range` (находка 65) настоящей микроструктурой.

**39. 🔵 ИДЕЯ: `/api/v5/public/liquidation-orders` для категории «ликвидации».** Сейчас вся
категория — расстояние до 30-барного экстремума (находка 62). Реальные ордера ликвидаций дают
объёмы и направления каскадов.

**40. 🔵 ИДЕЯ: `/api/v5/rubik/stat/*`.** Long/short ratio, taker buy/sell volume, история OI —
публичные агрегаты OKX, которых сейчас нет ни в одной категории. Это закрывает
`derivatives_positioning` и `sentiment_attention` настоящими данными.

**41. 🔵 ИДЕЯ: `/api/v5/market/index-tickers` + `/api/v5/public/mark-price`.** Индексная и mark-цена
дают настоящий базис спот/перп. Сейчас «межбиржевая дисперсия» = фандинг × 10000 (находка 58).

**42. 🔵 ИДЕЯ: `/api/v5/public/funding-rate-history`.** История фандинга позволяет считать z-score и
перцентиль, а не сравнивать с абсолютным порогом, который насыщается (находка 50).

**43. 🔵 ИДЕЯ: слой «data contract».** Каждая запись несёт `source`, `isLive`, `fetchedAt`,
`schemaVersion`, `provider`. Фичи наследуют провенанс; синтетика не пишется в БД никогда, а в
отчётах отдельной строкой видно, какая доля выборки настоящая.

# C. Feature Engine: 15 категорий (44–78)

**44. 🔴 Пороги годовой волатильности недостижимы.** `feature-engine.ts:154-155`:
`realizedVol > 0.08 → VOLATILE`, `< 0.02 → RANGING`. Реальная годовая волатильность крипты 40–90%.
**Замер:** 400 серий с annVol 35–90% → `{TRENDING_BEAR: 146, TRENDING_BULL: 141, VOLATILE: 113}`,
`RANGING` — 0 раз. 200 серий с annVol 8–12% (экстремально тихий рынок) → `VOLATILE` 142 раза (71%).
Пороги надо ставить в единицах, которые действительно измеряются (например, перцентиль σ актива
по его же истории), а не в абсолютных годовых.

**45. 🔴 Два режима недостижимы.** `detectRegime` физически не может вернуть
`LOW_VOLATILITY_SQUEEZE` и `LIQUIDITY_CRUNCH` (нет ни одной ветки). При этом
`feature-engine.ts:253` ссылается на `LOW_VOLATILITY_SQUEEZE`, а `REGIME_WEIGHT_DELTAS`
(`combination-engine.ts:14-23`) задаёт для них дельты. Мёртвый код + ложное обещание в UI
(фильтр режимов тоже их предлагает, см. 96).

**46. 🔴 Мёртвые ветки в определении тренда.** `feature-engine.ts:135-146`:

if (plusDI > minusDI) { if (ema9 > ema21 && ema21 > ema50) return "TRENDING_BULL"; return "TRENDING_BULL"; }

Обе ветки возвращают одно значение. EMA-стек вычисляется (`calculateEMAStack`) и выбрасывается.

**47. 🔴 Волатильность в `detectRegime` считается по СТАРЫМ барам.** `feature-engine.ts:148`:

**48. 🔴 ADX посчитан неверно.** `calculateADX` (строки 47-84): (а) `plusDM` и `minusDM`
накапливаются одновременно — по стандарту берётся только большая сторона; (б) нет сглаживания
Уайлдера (простая сумма по всей серии); (в) параметр `period = 14` используется только как проверка
минимальной длины, расчёт идёт по всем 60 барам. Итог: число, названное ADX, не является ADX и
переключает режим на шумных сериях.

**49. 🔴 Знак скора и направление в `derivatives_positioning` противоречат друг другу.**
`feature-engine.ts:334-345`: `fundingNorm = clip(−funding × 4000)` (контр-трендовая логика, описана

**50. 🔴 Фича фандинга насыщается и имеет постоянный уклон.** `clip(funding × 2000)` даёт ±1 уже при
|funding| ≥ 0.0005 (5 bps за 8 ч — обычное значение). Нейтральный базовый фандинг 0.0001 → постоянные
+0.2, то есть систематический UP-вклад в каждую связку, содержащую категорию. Разрешающая
способность между 0.0005 и 0.01 отсутствует полностью.

**51. 🔴 7 из 15 категорий — константы при отсутствии стакана/фандинга/OI.** **Замер** (300 состояний,
серии разные, book/funding/oi не переданы):

derivatives_positioning    sd = 0.0000   mean = 0.200
cross_exchange_dispersion  sd = 0.0000   mean = 0.245

**52. 🔴 Пропуск данных не обнуляет вклад.** `missingness` и `confidence` записываются

**56. 🔴 `sentiment_attention` — произведение двух других фич.** `feature-engine.ts:471-486`:

часы). Всё остальное — арифметические производные. `crossAgreement` (0–20 баллов, треть разброса EVS)

**59. 🟠 `time_calendar_session` задаёт постоянный UP-байас.** `feature-engine.ts:488-508`:
в окне 13:00–16:00 UTC `sessionScore = +0.4` → `direction = UP` каждый день в это время независимо

Её вес обучается на этой регулярности, а не на рынке.

**60. 🟠 Время берётся из `new Date()`, а не из свечи.** `feature-engine.ts:489`. При любом
бэктесте/реплее/дозагрузке истории сессионная фича получит ТЕКУЩЕЕ время — классическая утечка
календарного знания (ровно то, о чём предупреждает `research/references.txt` [19]).

**61. 🟠 `minutesToNextFunding` не сверяется с реальным `fundingTime`.** OKX возвращает
`fundingTime` и `nextFundingRate` в ответе (`types.ts:76-81`), но категория считает окно по модулю 8

**62. 🟠 Категория «ликвидации» — геометрический прокси.** `feature-engine.ts:349-372`:
расстояние до 30-барных max/min, `liqScore = (distToLow − distToHigh) × 15` при расстоянии больше
0.5%. Коэффициент 15 и порог 0.5% ничем не обоснованы; реальных данных о ликвидациях нет (см. 39).

**63. 🟠 `Math.max(...array)` по срезу свечей.** `feature-engine.ts:350-351`. На 30 элементах безопасно,
но при расширении окна до сотен/тысяч баров — `RangeError: Maximum call stack size exceeded`.

**64. 🟠 `order_book_microstructure`: часть вычислений выбрасывается.** `feature-engine.ts:294-325`:
`spreadBps` и `ir2pct` попадают только в `metadata`, в `normalizedScore` идёт один `bookImbalance × 1.5`.
Спред — ключевая величина для исполнимости (и уже используется в `universe.ts`) — здесь игнорируется.

**65. 🟠 `order_flow` — прокси без тейкерских данных.** `feature-engine.ts:266-291`: доля «агрессивных
покупок» = `(close − low) / (high − low)`. Это индикатор закрытия в диапазоне, а не поток. Свечи с

**66. 🟠 `volatility_regime` — константа по режиму, а не измерение.** `feature-engine.ts:243-264`:
`normalizedScore` = 0.6 / −0.6 / 0.35 / −0.2 в зависимости от `detectRegime`. Сама
`realizedVol` вычисляется и уходит в `rawValue`/`metadata`. Категория дублирует режим (и наследует
все его баги 44-48) вместо того, чтобы мерить волатильность.

**67. 🟠 Нормировка моментума не зависит от волатильности актива.** `feature-engine.ts:210-227`:
`momNorm = tanh(momReturn × 30)`. Коэффициент 30 одинаков для BTC (25 bps медианный ход за 15 мин,
замер) и для альткоина с ходом 200 bps. На тихом активе порог `|momNorm| > 0.15` почти недостижим,
на шумном — достигается всегда. Нужен z-score по σ самого актива.

**68. 🟠 Пороги `direction` захардкожены по категориям.** 0.15 / 0.1 / 0.2 / 0.25 / 0.4 — разные для
каждой фичи (строки 218–523). Базовые
частоты UP/DOWN у категорий разные → «согласие» систематически смещено в сторону категорий с
низким порогом. Ни один порог не калибруется по данным.

**69. 🟠 `cross_asset_relationships` для BTC — копия моментума.** `feature-engine.ts:390-408`:
при `symbol === "BTC-USDT"` подставляется `momReturn × 0.5`. **Замер:** r = 0.997 с `price_returns`.
Бета не вычисляется, хотя описание категории (`types.ts:173-178`) обещает «BTC/ETH beta, cointegration
residual z-score».

**70. 🟠 Окна актива и BTC не синхронизированы.** `feature-engine.ts:392-399`:
`btcCandles[len−20]` и `closes[len−20]` берутся по ИНДЕКСУ, а не по `timestamp`. Серии имеют разную
длину (якорь тянется с 60 барами, остальные — с 60, но добор для выбывших активов — с 24,
`autonomous-scheduler.ts:139`) → «relative strength» сравнивает разные периоды.

**71. 🟠 Breadth считается по-разному в разных местах.** В цикле — `floorTickers.slice(0, 150)`
(`autonomous-scheduler.ts:298-304`), в `/heatmap` — все ~450 тикеров без фильтра
(`heatmap/route.ts:33-37`). Одна и та же фича имеет разные значения на двух экранах и в двух
контекстах для ИИ.

**72. 🟡 Breadth по 24-часовому изменению слишком медленная для горизонта 15 минут.**
`change24h > 0` меняется в течение дня слабо → фича почти константа внутри суток (что и показал
замер sd = 0 при одном срезе тикеров).

**73. 🟡 `clip()` превращает NaN в 0.** `feature-engine.ts:34-37`. Ошибка вычисления неотличима от
нейтрального сигнала; `missingness` при этом остаётся 0.

**74. 🟡 Мёртвый код: `ema()`.** `feature-engine.ts:88-101` не вызывается нигде; используется только
`emaSimple`. Две реализации одного с разным поведением на коротких сериях.

**75. 🟡 `quoteAvg` делится на константу 20.** `feature-engine.ts:439`:
`candles.slice(-20).reduce(...) / 20` — при 10 свечах среднее занижено вдвое, `flowRatio` завышен.

**76. 🟡 `dataQualityScore` считает нулевой скор отсутствием сигнала.** `feature-engine.ts:547`:
`filter((s) => s.normalizedScore !== 0)`. Легитимный нейтральный сигнал штрафуется как пропуск.

**77. 🔵 ИДЕЯ: слой примитивов вместо «категорий».** 40–80 честных примитивов (каждый — одна
измеримая величина с провенансом), категории — только группы для отчётности. Перед включением в

**78. 🔵 ИДЕЯ: point-in-time нормировка.** Каждый примитив → rolling z-score или квантильное

# D. Combination Engine и Early Value Score (79–98)

**79. 🔴 `lookback` не влияет ни на что, кроме подписи.** `combination-engine.ts:176-311`: параметр
`lookback` используется только в `expression` (строка 278) и в `parameters.lookback`. Все скоры
берутся из уже готовых `signals`. **Замер:** из 100 связок уникальных «поведений»
(категории + оператор + порог) — 81, то есть 19 связок являются полными дублями по поведению,
отличаясь только декоративным lookback.

**80. 🔴 Дубли при этом получают РАЗНЫЕ подписи стратегии.** `planner.ts:141-147`:
`signatureOf(asset, categories, direction, {lookback, threshold})`. **Замер:**
```
BTC-USDT|order_flow+price_returns|UP|lb7-th0.4
BTC-USDT|order_flow+price_returns|UP|lb14-th0.4
BTC-USDT|order_flow+price_returns|UP|lb21-th0.4
BTC-USDT|order_flow+price_returns|UP|lb50-th0.4
```
История одной стратегии размазана по 4 ключам → `n` каждой подписи вчетверо меньше, порог
значимости `MIN_SIGNIFICANT_N = 5` (`planner.ts:454`) почти не достигается, приор для модели
всегда «незначим». Обучение не накапливается именно там, где должно.

**81. 🔴 Перебор пар обрывается на 30 и покрывает только первые категории.**
`combination-engine.ts:53-79`: двойной цикл с `break` при `combinations.length >= 30` перебирает
пары лексикографически, поэтому в «попарный» блок попадают почти только пары с участием
`price_returns`, `volume_liquidity`, `volatility_regime`. **Замер:** покрыто 73 из 105 возможных пар
категорий; 32 пары (например, `stablecoin_flow_proxies + time_calendar_session`) не появляются
ни в одном из 100 вариантов никогда.

**82. 🔴 Хвост перебора добивается одной и той же четвёркой.** `combination-engine.ts:145-172`:
`while (combinations.length < 100)` генерирует связку из фиксированных
`[price_returns, derivatives_positioning, liquidations, anomaly_novelty]` с 4 порогами и 2 операторами.
До 10 «разных» связок в конце списка — одна и та же идея.

**83. 🔴 EVS — не ожидаемая доходность, а сумма почти констант.** **Замер** среднего вклада
компонент на 100 связках одного состояния:
```
novelty 9.29 | crossAgreement 0.96 | historicalSupport 4.37 | effectStability 7.00
coverageLiquidity 8.91 | dataQuality 10.00 | testability 2.00 | ИТОГО 42.53
```
Из 100 баллов 30 (stability + liquidity + quality + testability) — детерминированные константы,
не зависящие от связки. Реально различают связки только `novelty` и `crossAgreement`.
Ранжирование «топ по EVS» — это ранжирование по |anomaly| и по числу согласных дублей.

**84. 🔴 `novelty` = модуль `anomaly_novelty`.** `combination-engine.ts:240`:
`Math.abs(anomalySig) × 15`. «Новизна» связки не сравнивается ни с историей этой связки, ни с тем,
как часто её тестировали. Компонента с весом 20/100 измеряет то, что уже учтено в другой фиче (57).

**85. 🔴 `historicalSupport` = длина окна данных.** `combination-engine.ts:246-249`:
`min(supportCount)/2`, а `supportCount` в сигналах — это `len` (число свечей) или 20
(`feature-engine.ts:193,222,239,467,524`). Компонента «историческая поддержка эффекта» измеряет, сколько
свечей мы скачали. При 60 свечах она всегда равна 20/20 — максимум.

**86. 🔴 `sampleSize = minSupport` выдаётся модели как число наблюдений.**
`combination-engine.ts:308` → `planner.ts:496` (`n=${c.sampleSize}`) → промпт планировщика.
Модель читает «n=60» как 60 прошлых исходов стратегии, хотя это 60 свечей в окне.
Прямая дезинформация принимающего решения.

**87. 🟠 `crossAgreement` почти всегда 0–1 из 20.** **Замер:** среднее 0.96 при 81% связок
в состоянии NEUTRAL. Причина — пороги 0.25–0.60 применяются к `avgScore`, который у большинства
категорий меньше. В итоге EVS связок различается на единицы баллов, а отбор «топ-2 по активу»
фактически случаен.

**88. 🟠 `selectUniverse` имеет побочный эффект в read-only пути.** `universe.ts:382`:
`noteUniversePresence(chosen...)` мутирует модульный `streaks`. Функция вызывается и из
`loadActiveUniverse()` (`universe-store.ts:73`) — то есть обычный GET `/status` меняет
anti-crowding-состояние и счётчик `scanFallbacks`, влияя на следующий настоящий цикл.

**89. 🟠 Нормировка композита несогласована.** `combination-engine.ts:187-205`:
`compositeScore += score × (weight + regimeDelta)`, а `totalWeight = Σ weight` БЕЗ `regimeDelta`.
При `regimeDelta ≠ 0` делитель не соответствует числителю → композит смещён на
`regimeDelta × Σscore / Σweight`, величина смещения зависит от состава связки.

**90. 🟠 `REGIME_WEIGHT_DELTAS` — сдвиг всех весов, а не режимная настройка.**
`combination-engine.ts:14-23,198`: дельта прибавляется одинаково к каждой категории. Для
`TRENDING_BEAR` это −0.1 ко всем весам, то есть просто уменьшение композита, а не «в медвежьем
режиме доверяй другим категориям». Нужна матрица regime × category.

**91. 🟠 Статусы связок недостижимы.** `combination-engine.ts:270-275`: `promising` требует
EVS ≥ 75 И agreementRatio ≥ 0.75. **Замер** распределения EVS на реалистичном состоянии:
`max = 74, p75 = 45, median = 41, min = 36`. Статус `promising` не присваивается практически
никогда; `rejected` (EVS < 40) — тоже редко. В БД и в UI почти всё «candidate» навсегда.

**92. 🟠 Оператор VETO проверяет две фиксированные категории.** `combination-engine.ts:217-231`:
всегда `derivatives_positioning` против `price_returns`, независимо от того, какие 4–5 категорий
в связке. «VETO-связка из liquidity+anomaly+session» голосует по категориям, которых в ней нет.

**93. 🟠 AND-оператор практически мёртв.** `combination-engine.ts:209-215`: требует, чтобы ВСЕ
категории превысили порог в одну сторону. При константных и слабых фичах (51, 87) это редкость —
**замер:** 19 UP из 100 связок, DOWN — 0 в том состоянии. Пространство поиска сужено до WEIGHTED/OR.

**94. 🔴 Таблица `combinations` заморожена на первом наблюдении.** Код связки детерминирован
(`C2-BTC-USDT-001`), а `autonomous-scheduler.ts:377-397` вставляет запись только если кода ещё нет.
Содержание (EVS, скоры, статус) пересчитывается каждый цикл и выбрасывается. В БД лежит срез
ПЕРВОГО цикла навсегда.

**95. 🔴 ИИ-контекст читает этот замороженный срез.** `context.ts:186-190`: топ-12 комбинаций
по EVS из всей таблицы без фильтра по времени и без привязки к последнему циклу. Аналитик
(и планировщик через `weightsTop`) рассуждает о связках недельной давности, считая их текущими.

**96. 🟠 Фильтр режимов предлагает режимы, которых не существует, и не предлагает существующие.**
`filters.ts:7-15`: в `ALL_REGIMES` есть `LOW_VOLATILITY_SQUEEZE` и `LIQUIDITY_CRUNCH` (недостижимы,
см. 45), но нет `RANGING` и `VOLATILE` (которые `detectRegime` возвращает чаще всего). Режимный
замок нельзя выставить на реальный режим рынка.

**97. 🟡 `parameters.weights` дублирует всю карту весов в каждую связку.**
`combination-engine.ts:300-305`: объект из 15 весов пишется в `parametersJson` каждой из 25
сохраняемых связок каждого цикла. Раздувание JSONB без пользы — веса и так лежат в `learning_weights`.

**98. 🔵 ИДЕЯ: заменить перечисление на поиск с бюджетом.** DSL выражений
(`AND/OR/NOT/ZSCORE(primitive, window) > k`), дедуп по каноническому хэшу выражения, beam search
по univariate lift → парные → тройки, и ЯВНЫЙ счётчик испытаний для поправки на отбор (см. 147).

# E. Гипотезы, прогнозы и разрешение исходов (99–122)

**99. 🔴 Горизонт и барьеры не масштабируются волатильностью.** `hypothesis-engine.ts:56`:
`deltaPct = 0.0045` для всех активов. **Замер:** медианный ход BTC за 15 мин ≈ 25 bps, бар
исхода 35 bps достигается в 31% шагов; у актива с annVol 12% медиана 4 bps и бар достигается в 0%
шагов. Один и тот же прогноз для BTC — тест, для тихого альта — гарантированный miss.

**100. 🔴 Записанные цель/инвалидация не используются при разрешении.** `hypothesis-engine.ts:57-77,118-129`
пишет `targetPrice`, `invalidationPrice`, `targetCondition` («price ≥ X до момента Y»), а
`outcome-evaluator.ts:60-90` считает hit по своим константам: `mfe > 0.35%` И
`rawReturn > 0.24%`. Пре-регистрированное утверждение и фактически проверенное — разные утверждения.
Это нарушает базовый принцип всей затеи («на листике пишу прогноз, потом проверяю ЕГО»).

**101. 🔴 Утечка назад: свечи до фиксации прогноза попадают в окно.** `outcome-evaluator.ts:45`:
`candles.filter(c => c.timestamp >= fixedTime - 15 * 60 * 1000)`. **Замер:** свеча со скачком
100 → 1000 за 15 минут ДО `fixedAt` даёт `mfe = 900%` при цене на горизонте 100.05. Любой
предшествующий всплеск засчитывается как «благоприятная экскурсия» прогноза.

**102. 🔴 Утечка вперёд: верхней границы окна нет.** В том же фильтре отсутствует
`c.timestamp <= resolveTime`. **Замер:** свеча через 1 час 45 минут ПОСЛЕ `resolveAt` дала
`mfe = 3.000%`. Если цикл задержался (а он запускается то через 14, то через 29 минут),
в «15-минутный» прогноз попадает полчаса-час будущего.

**103. 🔴 Горизонт плавает от 15 до 45+ минут.** `resolvedPrice`/`rawReturn` берутся из
`currentPrice` = цена тикера В МОМЕНТ РАЗРЕШЕНИЯ (`autonomous-scheduler.ts:230`), а не цена на
`resolveAt`. При цикле каждые 14 минут и горизонте 15 минут разрешение происходит на следующем
или через следующий цикл. Разные прогнозы измеряются на разных горизонтах, а сравниваются как равные.

**104. 🔴 `hit` смешивает два разных утверждения.** `outcome-evaluator.ts:69,75`:
`rawReturn > издержки И mfe > 0.35%`. Это одновременно «терминальная доходность положительна» и
«путь задел цель». Полученная метрика — не точность направления, не PnL сделки и не вероятность.
Собственный протокол (`research/README.md`) требует разделять эти четыре вещи.

**105. 🔴 `ambiguous` недостижим, `expired` не используется.** `outcome-evaluator.ts:87-88`:
`isMiss = !isHit` во всех ветвях, поэтому `outcome` всегда `hit` или `miss`. Схема
(`forecasts.outcome`) и типы (`types.ts:35`) обещают 4 значения; UI (`status/route.ts:60`) считает
`ambiguous` — всегда 0.

**106. 🔴 Ветка RANGE структурно убыточна.** `outcome-evaluator.ts:79-84`:
`rawReturn = 0.3 − movePct`, издержки 0.24% → максимум +0.06% даже при идеально нулевом движении.
Любая RANGE-гипотеза обречена на отрицательный expectancy по построению, а не по рынку.
К тому же `mae = 0` всегда, что ломает `profitFactor = avgMfe/avgMae` в `/walkforward`
и `avgMae` в `/edge`.

**107. 🟠 Издержки — константы, хотя реальный спред уже получен.** `hypothesis-engine.ts:154-156`:
`costsBps 8 / slippageBps 3 / fundingDragBps 1`. Стакан запрошен в том же цикле
(`autonomous-scheduler.ts:310`) и содержит настоящий спред. Funding drag начисляется каждому
прогнозу, хотя фандинг платится раз в 8 часов (вероятность попасть в окно ≈ 1/32) — систематическое
завышение издержек на ~1 bpс и занижение expectancy.

**108. 🟠 Издержки вычитаются из прогноза, который не является сделкой.** Система «просто записывает
прогноз» (по замыслу), но метка требует доходности ПОСЛЕ round-trip издержек. Для измерения
точности направления издержки не нужны; для измерения PnL нужна модель входа/выхода. Сейчас
ни то, ни другое не измерено честно.

**109. 🟠 Пропавший тикер молча превращается в «слабый сигнал».** `autonomous-scheduler.ts:236`:
`tickers.find(...)?.last || fc.entryPrice`. Если актив делистнут/не попал в ответ, `currentPrice`
= цена входа → `rawReturn = 0` → `miss` с `errorType = weak_signal`. Таксистика ошибок learns на
фантомных причинах вместо `data_gap`.

**110. 🟠 Классификатор ошибок: 5 из 10 типов недостижимы.** `outcome-evaluator.ts:93-107` выставляет
только `cost_drag`, `wrong_horizon`, `wrong_sign`, `weak_signal`, `regime_mismatch`.
`insufficient_liquidity`, `category_conflict`, `external_event`, `data_gap`, `none` (для hit) не
присваиваются никогда, хотя описаны в типах (`types.ts:37-47`), в справочнике `/edge`
(строки 251-261) и в «лечении» glassbox (`glassbox.ts:4-11`).

**111. 🟠 Магические проценты в классификаторе.** `outcome-evaluator.ts:96-104`: 0.4 / −0.2 / −0.7 /
0.15 — абсолютные проценты, одинаковые для BTC (ход 25 bps) и для альта (ход 300 bps).
Для волатильного актива почти всё попадает в `wrong_sign`, для тихого — в `weak_signal`.

**112. 🟠 Статус гипотезы обновляется только при наличии `hypothesisId`.**
`autonomous-scheduler.ts:262-280`: если у прогноза нет привязки (или она потеряна), гипотеза
остаётся `active` навсегда. `status/route.ts:26-31` считает «активные гипотезы» — число растёт
монотонно и ничего не означает.

**113. 🟠 Два разных смысла в одном поле `uncertainty`.** `hypothesis-engine.ts:106` считает её из EVS,
`autonomous-scheduler.ts:513` перезаписывает из `1 − conviction` модели. Значение из draft теряется,
а калибровка (133) и «уверенность» в `/planner` (`loadSelectionRecord`) читают одно поле, не зная,
кто его заполнил.

**114. 🟠 Код гипотезы может столкнуться и уронить цикл.** `hypothesis-engine.ts:51-52`:
`timestamp.slice(-8)` + `Math.floor(Math.random() * 9000 + 1000)`. При потолке 12–30 гипотез на цикл
вероятность коллизии мала, но `hypotheses.code` имеет UNIQUE-ограничение, а вставка не обёрнута в
try/catch → конфликт прерывает цикл после частичных записей (см. 10, 11).

**115. 🟠 `checksum` вычисляется и никогда не проверяется.** `hypothesis-engine.ts:131-137` считает
SHA-256, `forecasts.checksum` — `notNull`. Ни один код не пересчитывает и не сверяет его.
«Криптографическая неизменяемость прогноза» декоративна: изменить строку в БД можно, и никто не узнает.

**116. 🟠 Одна связка = один прогноз = одна точка данных.** На цикл создаётся ≤ 12 прогнозов,
повторные измерения той же подписи в других бакетах не планируются специально. С учётом находки 80
(размывание по lookback) накопление значимой статистики по подписи занимает месяцы.

**117. 🟡 `entryPrice` = последняя сделка, а не сторона стакана.** Для гипотезы UP реалистичный вход
— ask. Систематическая недооценка издержек на полспреда (для ликвидных пар ~0.5–1 bps, для
пограничных — до 5 bps, что сравнимо со всем баром 35 bps).

**118. 🟡 `expectedMinPrice/expectedMaxPrice` — произвольные коэффициенты.**
`hypothesis-engine.ts:60-77`: `×1.002`, `×0.998`, `×0.8`, `×1.5`. В разрешении не используются,
в UI показываются как «ожидаемый диапазон».

**119. 🟡 Горизонт захардкожен в вызове.** `autonomous-scheduler.ts:505-509`: литерал `15` с
комментарием, хотя схема и типы поддерживают любой `horizonMinutes`. Сетки горизонтов нет.

**120. 🔵 ИДЕЯ: метка «тройной барьер» с волатильностным масштабом.** target = k·σ_15m(актив),
stop = m·σ_15m, time = конец бакета. Барьеры считаются на момент фиксации и замораживаются вместе
с checksum. Разрешение — «какой барьер первый», а не «mfe > 0.35%».

**121. 🔵 ИДЕЯ: три исхода на каждый прогноз, а не один.** (а) знак доходности на горизонте
(точность направления), (б) первый барьер (качество сетапа), (в) PnL симулированной сделки с
реалистичной моделью издержек (экономика). Три разные метрики, три разные цели оптимизации.

**122. 🔵 ИДЕЯ: отдельный джоб разрешения.** Читает только сохранённые свечи в
`[fixedAt, resolveAt]`, выполняетcя один раз, пишет immutable-вердикт + сверку checksum, при
отсутствии данных ставит `expired`/`data_gap`. Генерация и разрешение не зависят друг от друга.

# F. Обучение, веса и калибровка (123–142)

**123. 🔴 Полное «переобучение» после каждого цикла двойит всю историю.** `autopilot.ts:66-88`:
берутся ВСЕ resolved-прогнозы и прогоняются через `learningLoop.updateFromOutcomes`, которая
ИНКРЕМЕНТИРУЕТ `totalSamples/totalHits/totalMisses` (`learning-loop.ts:108-131`). После k циклов
каждый исторический исход учтён ~k раз: n растёт квадратично, приор α=β=5 теряет смысл,
скользящее среднее Brier переписывается заново.

**124. 🔴 Плюс инкремент в самом цикле — новые исходы считаются дважды.**
`autonomous-scheduler.ts:284-288` (шаг 4) уже применил только что разрешённые события; затем
`autopilot.ts:82-84` применяет их ещё раз в составе «всей истории».

**125. 🔴 Brier не измеряет калибровку системы.** `learning-loop.ts:117-120`:
`forecastProb = clamp(smoothedWinRate)` — апостериорный win-rate ТОЙ ЖЕ категории по ТЕМ ЖЕ данным.
Метрика само-ссылочна и по построению близка к оптимальной. Настоящая предсказанная вероятность
системы — `1 − hypotheses.uncertainty` — в расчёте не участвует. Все экраны «Brier 0.19 = хорошая
калибровка» показывают фикцию.

**126. 🔴 Кредит распределяется поровну между всеми категориями связки.**
`learning-loop.ts:104-131`: hit повышает счётчики каждой из 2–5 категорий гипотезы одинаково,
включая ту, которая указывала в противоположную сторону. Классическая ошибка кредит-ассигнации;
вес «хорошей» категории растёт за счёт плохой и наоборот.

**127. 🔴 `priorWeight` никогда не обновляется.** `learning-loop.ts:124`:
`newWeight = priorWeight × multiplier`, а `priorWeight` всегда 1.0 (строка 34, никогда не пишется).
«Байесовское обновление» — это просто функция от накопленного win-rate; истории весов нет,
откатить или проаудировать траекторию обучения нельзя.

**128. 🟠 Формула веса ловит состав выборки, а не качество категории.**
`multiplier = (smoothedWinRate / 0.5)^0.75` (строка 123). Базовая частота `hit` зависит от актива,
бара 35 bps и режима, а не только от категории. Категория, которая часто попадала в связки на
волатильных альтах, получит высокий вес без всякой предсказательной силы.

**129. 🟠 Режимный разрез объявлен, но не реализован.** `learningWeights.regimePerformanceJson`
создаётся пустым (`learning-loop.ts:40`) и никогда не заполняется. При этом
`edge/route.ts:219-240` строит по нему «матрицу режимов», а `edge-view.tsx` её рисует → экран
навсегда пустой. То же с `leaderboard.regimes: [] as string[]` (строка 211).

**130. 🟠 Нет разрезов по активу, горизонту, оператору, режиму.** Обучение глобальное: один вес
категории на всю лабораторию, хотя связки строятся на конкретных активах с конкретной волатильностью.

**131. 🟠 Нет затухания по времени.** Ни экспоненциального decay, ни скользящего окна: веса
усредняют всю историю с равным весом. Смена режима рынка полгода назад и сегодняшний день влияют
одинаково (а с учётом 123 — вчерашний день влияет в k раз сильнее).

**132. 🟠 N+1 запросы в обучении.** `ensureInitialized` делает 15 SELECT'ов (+ до 15 INSERT'ов)
и вызывается в начале каждого цикла, в `getWeightsMap` и в `getAllStats`; `updateFromOutcomes`
пишет 15 UPDATE'ов построчно, без транзакции.

**133. 🟠 Калибровочные бины схлопываются.** `uncertainty` ограничена `[0.1, 0.6]`
(`autonomous-scheduler.ts:513`), `predictedProb` дополнительно клампится в `[0.40, 0.85]`
(`learning/route.ts:56`) → почти все предсказания попадают в 1–2 бина из 4. Reliability-диаграмма
не может показать ничего.

**134. 🟠 `learningUpdatesCount` — константа.** `autonomous-scheduler.ts:629`: `learningUpdated ? 15 : 0`.
Метрика «сколько обновлений обучения произошло» не измеряется.

**135. 🟠 Нет журнала «до/после» весов.** В `experimentRuns` пишется только `avgBrier`
(`learning-loop.ts:151-161`). Невозможно ответить, что обучение сделало с весами за цикл и почему.

**136. 🟡 `totalAccumulatedSamples` в UI завышен в разы.** `learning/route.ts:85` суммирует
`totalSamples` по 15 категориям: один исход даёт 2–5 «сэмплов». Цифра «накоплено N наблюдений»
не равна числу наблюдений (и дополнительно умножена на k из-за 123).

**137. 🟡 Веса почти не влияют на результат.** Они входят только в `compositeScore` (и то с
несогласованной нормировкой, см. 89) и не влияют на пороги направлений, на отбор категорий и на EVS
напрямую. Обучение меняет ранжирование связок в пределах единиц баллов.

**138. 🟡 `experimentRuns` пишется и из обучения (`runType: "online_learning_update"`),
и из цикла — в одной таблице смешаны разные сущности, а `regimeDetected: "ADAPTIVE"` не является
режимом из `MarketRegime`.

**139. 🔵 ИДЕЯ: настоящая модель вместо 15 весов.** Датасет = снапшоты фич (уже пишутся в
`signal_features`, но без привязки к исходу — см. 176) + метка тройного барьера. Обучать логистическую
регрессию/градиентный бустинг с purged k-fold + embargo, калибровать изотоникой, считать важности
и частичные зависимости. Веса категорий останутся как интерпретируемый fallback.

**140. 🔵 ИДЕЯ: мета-маркировка.** Первичный сигнал (детерминированный) + вторичная модель
«стоит ли брать этот сигнал» с выходом в вероятность. Вероятность и есть `forecastProb` для честного
Brier; решение о ставке — по порогу вероятности, а не по «уверенности» LLM.

**141. 🔵 ИДЕЯ: онлайн-обучение с полураспадом.** Экспоненциально взвешенные окна (half-life 7–30
дней) + отдельный «холодный» holdout-слой, который обучение не трогает никогда.

**142. 🔵 ИДЕЯ: честные A/B-армы.** Сейчас `loadSelectionRecord` (`planner.ts:255-300`) смешивает
«правило по просьбе человека» и «fallback из-за недоступности модели» в одну армию `rule` —
сравнение «ИИ против детерминизма» загрязнено. Нужны отдельные армы: ai / rule / random /
momentum-baseline, с назначением по детерминированному ключу бакета и статтестом различий.

# G. Статистика: утечки, множественные сравнения, holdout (143–155)

**143. 🔴 Бенчмарки walk-forward захардкожены.** `walkforward/route.ts:59-84`:
`randomGuess 48.2% / −12.4 bps`, `buyAndHold 52.1% / +8.5`, `simpleMomentum 53.4% / +11.2`.
Эти числа нигде не вычисляются, но выводятся рядом с реальной метрикой и участвуют в вердикте
`isHoldoutRobust` (строка 86) и в промпте glassbox (`glassbox.ts:120`: «модель обязана бить простой momentum ≈53.4% / +11.2 bps»). Это имитация расчёта — то, что `research/README.md`
запрещает прямо.

**144. 🔴 «Аудит утечек» — строковая константа.** `walkforward/route.ts:106`:
`leakageAudit: "PASSED: Strict chronological ordering, purged overlaps, forward horizon calculation only."`
Purging и embargo не реализованы нигде в коде; утечки в окне разрешения (101, 102) есть.
Экран сообщает пользователю, что проверка пройдена, когда она не проводилась.

**145. 🔴 Синтетический seed смешивается с реальными данными во всех расчётах.**
`seed/route.ts` создаёт ~80 выдуманных исходов с заранее заданным числом hits, и они попадают в
train/holdout (`walkforward`), в лидерборд (`edge`), в приоры (`loadSignatureHistory`) и в веса.
Пометки «это синтетика» нет ни в одной таблице.

**146. 🔴 Holdout пересчитывается и показывается постоянно.** `walkforward` опрашивается UI каждые
60 секунд (`app-shell.tsx:196`). Исследователь (человек или ИИ) видит holdout сотни раз и может
подстроить под него отбор — holdout перестаёт быть out-of-sample. Нужен одноразовый, запертый
holdout с журналом обращений.

**147. 🔴 Нет ни одной поправки на множественные сравнения.** Каждый цикл перебирается 100 связок
на актив × 8–10 активов = до 1000 кандидатов, из них отбираются лучшие по EVS, затем лучшие по
итогам. Ни White Reality Check, ни Hansen SPA, ни Deflated Sharpe, ни PBO — хотя все они
перечислены в собственном библиографическом ядре (`research/references.txt` [1]–[5]).
При таком переборе «найдена рабочая связка» — ожидаемый результат даже на чистом шуме.

**148. 🔴 Одна и та же подпись пере-тестируется бесконечно.** `autonomous-scheduler.ts:438-450`:
`excludeSignatures` строится только из PENDING-прогнозов. Как только прогноз разрешился, связка
снова доступна; её накопленная статистика подаётся модели как приор (`renderPrior`), и модель
склонна брать то, что уже «хорошо себя показало». Это самоподкрепляющийся отбор с сильной
selection bias.

**149. 🟠 Перекрывающиеся метки и отсутствие весов по уникальности.** Прогнозы по одному активу
с горизонтом 15 мин и циклом 14 мин перекрываются; соседние исходы коррелируют. `uniqueness`
не считается, наблюдения не взвешиваются → эффективный объём выборки сильно меньше заявленного n.

**150. 🟠 Wilson-интервал применяется к зависимым наблюдениям.** `context.ts:160-165`,
`edge/route.ts:22-30`. Формула предполагает независимость; при автокорреляции интервал занижен,
а пороги «n ≥ 8 и LB ≥ 55%» дают ложную уверенность.

**151. 🟠 Пороги валидности не привязаны к base rate.** 55% Wilson LB и 52% hit-rate
(`glassbox.ts:152-160`) — произвольные числа. Base rate зависит от бара 35 bps и волатильности
актива: на BTC бар достигается в 31% шагов (замер), значит «hit» — редкое событие по построению,
и 52% недостижимы даже для идеального предсказателя направления.

**152. 🟠 Нулевая гипота не измеряется.** Правильный baseline — «случайное направление на тех же
активах в тех же бакетах с тем же баром» — вычисляется из `computeMoveStats` почти бесплатно, но
нигде не используется. Вместо него — константы из 143.

**153. 🟠 `avgReturn` делится на все строки, включая нерезолвленные.** `walkforward/route.ts:37`:
`Σ(realizedReturnNet || 0) / set.length`, где `set` — все прогнозы окна, включая `pending` с `null`.
Метрика систематически стянута к нулю; hit-rate при этом считается только по hit+miss. Знаменатели
несогласованы.

**154. 🟠 `profitFactor = avgMfe / avgMae`.** `walkforward/route.ts:40`. Это отношение экскурсий,
а не profit factor (gross win / gross loss). При `mae = 0` (все RANGE) подставляется 1.2 —
выдуманное число. В `/edge` считается настоящий profit factor с тем же именем → два разных
показателя под одной этикеткой.

**155. 🔵 ИДЕЯ: реестр испытаний и «испытательный бюджет».** Таблица `trials(hypothesis_signature,
params_hash, bucket, verdict, registered_at, protocol_hash)`. Каждой сигнатуре выдаётся бюджет
(например, 20 испытаний), после чего она замораживается. Финальная оценка — один проход по
запертому holdout с Deflated Sharpe, где число испытаний N известно из реестра.

# H. LLM-слой: планировщик и аналитика (156–175)

**156. 🔴 Захардкоженные «резервные» API-ключи.** `provider.ts:43` —
`apiKey: "nvdia-fallback-key-must-replace"` (с опечаткой в слове nvidia), `provider.ts:111` —
`apiKey: "sk-fallback-must-replace"` на `api.openai.com`. Оба отправляются в реальные запросы
`Authorization: Bearer ...`. Это гарантированный 401, мусорный трафик и плохая секрет-гигиена
(сканеры секретов помечают репозиторий).

**157. 🔴 SSRF + эксфильтрация ключа через `baseUrl`.** `settings.ts:88-93`: `sanitizeUrl` пропускает
любой `http(s)://хост`, включая `http://127.0.0.1:...`, `http://169.254.169.254/` и внутренние
адреса. `PUT /api/research/ai-settings` не аутентифицирован. Злоумышленник ставит свой baseUrl —
и сервер отправляет туда запрос вместе с сохранённым API-ключом.

**158. 🔴 Ключи провайдеров хранятся в БД в открытом виде.** `ai_provider_settings.configs` (JSONB)
содержит `apiKey` plaintext (`settings.ts:170-190`). Любой доступ к БД/дампу/бэкапу = компрометация
ключей. Нужны env/secret-manager и шифрование at rest минимум.

**159. 🔴 Все эндпоинты без аутентификации.** `POST /api/research/reset` стирает всю историю
(`TRUNCATE ... CASCADE`, `reset/route.ts:21-23`) по `{confirm:true}`; `/cycle` запускает цикл;
`/ai-settings` меняет ключи и URL; `/filters` и `/policy` меняют параметры отбора. Автономная
система, доступная любому, кто узнал URL.

**160. 🟠 Сырой ответ модели не сохраняется.** `planCycle` (`planner.ts:640-740`) держит `raw`
в локальной переменной; в `experimentRuns.metricsJson.planner` уходят только picks/narrative/error.
Разобрать, почему модель решила именно так, и воспроизвести решение невозможно.

**161. 🟠 Промпт не версионируется.** `renderPlanPrompt` меняется вместе с кодом, но ни хэш промпта,
ни версия схемы контекста не сохраняются. История решений «ИИ vs правило» становится
несопоставимой после любой правки текста.

**162. 🟠 Недетерминированный отбор без журнала.** `temperature: 0.2` (`provider.ts:170`), нет `seed`,
нет `response_format: {"type":"json_object"}` / structured outputs / function calling. Одно и то же
состояние рынка даёт разные решения, и доказать это задним числом нельзя.

**163. 🟠 Разбор JSON хрупкий.** `extractJsonObject` (`planner.ts:420-445`) ищет первую `{` — проза
с фигурной скобкой до JSON ломает парсинг. `finish_reason === "length"` (обрезанный ответ из-за
`PLANNER_MAX_TOKENS = 700`) не обрабатывается: молчаливый уход в fallback без внятной причины.

**164. 🟠 Нет circuit breaker на цепочке провайдеров.** `planner.ts:663-690`: каждый цикл перебирает
всех включённых провайдеров с таймаутом до 40 с суммарно. Мёртвый провайдер (например, gpt4free
без ключа) тратит бюджет каждого цикла. Нет счётчика ошибок, нет исключения из цепочки, нет
метрики доступности.

**165. 🟠 Нет учёта токенов и стоимости.** `callProvider` читает `usage` из ответа
(`provider.ts:177-180`) и выбрасывает его. Для автономной системы, работающей 24/7, отсутствие
бюджета и алерта по расходам — прямой риск.

**166. 🟠 Калибровочные бины LLM-уверенности бессмысленны.** `clampConviction` ограничивает
conviction диапазоном [0.4, 0.9] (`planner.ts:544-549`), далее `uncertainty = 1 − conviction ∈ [0.1,0.6]`,
далее `predictedProb` клампится в [0.40, 0.85] (133). «Уверенность» языковой модели не калибрована
по построению, а здесь ещё и сжата в узкий диапазон.

**167. 🟠 Для ИИ-ветки нет лимита на актив.** `rulePick` соблюдает `perAsset = 2`
(`planner.ts:582-596`), а валидация ответов модели (`planner.ts:700-730`) проверяет только
«код из списка», дубли и потолок. Модель может взять все 12 пиков по одной монете → коррелированная
экспозиция и 12 почти одинаковых исходов в обучении.

**168. 🟡 Двойная валидация пиков.** `planCycle` валидирует коды по `candidates`, а
`autonomous-scheduler.ts:433,494-496` ищет `pick.code` в `poolByCode` (более широкий `eligible`).
Логика раздвоена; безопаснее возвращать из планировщика сами объекты кандидатов.

**169. 🟡 Контекст содержит константы вместо данных.** В промпте планировщика
(`planner.ts:521-527`) «издержки ~24 bps round-trip» и «бар 35 bps» — литералы, хотя `costsBps`
хранится в каждом прогнозе и может отличаться. При изменении модели издержек промпт начнёт врать.

**170. 🟡 `glassbox.ts` выдаёт рекомендации, которых система не умеет исполнять.** Например
«частичная фиксация 50% позиции при MFE ≥ 0.35%» (строка 7), «включить режимный замок» (строка 8),
«фильтр RVOL ≥ 1.4 перед входом» (строка 10). Ни частичной фиксации, ни RVOL-фильтра в движке нет:
детерминированный «аналитик» советует несуществующие механизмы.

**171. 🟡 `parseParamsFromText` меняет параметры лаборатории по регулярке из текста модели.**
`provider.ts:213-227` + `ai/route.ts:154-157`: строка «ПАРАМЕТРЫ: EVS=72, категорий=3» в ответе
LLM становится рекомендацией, которая в UI применяется к фильтрам. Автоматически не применяется —
но один клик, и свободный текст модели управляет отбором. Нужен явный schema-валидированный канал.

**172. 🟡 `MARKET_RE`-эвристика для smalltalk.** `provider.ts:136-146`: сообщение длиннее 60 знаков
или с цифрой считается «предметным» и тянет полный контекст БД (3000+ знаков) в каждый запрос.
«Сколько будет 2+2?» уходит в аналитический промпт вместе со всей статистикой лаборатории.

**173. 🟡 `isSmallTalkQuestion` зависит от порядка полей, а контекст болтовни всё равно пишется в БД.**
`ai/route.ts:80-125` сохраняет smalltalk в `ai_analyses` — таблица памяти лаборатории растёт мусором
(исключается только из выборки памяти, `context.ts:208`).

**174. 🔵 ИДЕЯ: разделить роли LLM.** (1) **Генератор** гипотез — выдаёт DSL-выражения по схеме
(валидация, дедуп по хэшу, лимит на цикл); (2) **критик** — ищет причины, почему гипотеза ложна;
(3) **интерпретатор** — объясняет накопленную статистику человеку. Отбор «что тестировать» должен
решать статистический критерий с поправкой на число испытаний, а не «уверенность» модели.

**175. 🔵 ИДЕЯ: журнал `llm_calls`.** Каждая запись: `decision_id`, `prompt_hash`, полный промпт,
полный ответ, provider, model, температура, токены, латентность, стоимость, версия кода (git SHA),
версия схемы контекста. Без этого автономная система необучаема в части «что именно решало».

# I. База данных, схема, производительность (176–187)

**176. 🔴 `signal_features` не связаны ни с чем.** В таблице (`schema.ts:34-47`) нет ни
`forecastId`, ни `hypothesisId`, ни бакета; `timestamp` = момент вставки
(`autonomous-scheduler.ts:349`), а не время свечи. Накопленные снапшоты фич невозможно соединить
с исходами → **единственный потенциальный обучающий датасет системы unusable**. Это главный
технический барьер для цели «обучаться на накопленных данных».

**177. 🔴 Миграций нет.** Каталога `drizzle/` в репозитории нет, скриптов `db:generate`/`db:push`/
`db:migrate` в `package.json` нет. Raw-SQL `CREATE TABLE IF NOT EXISTS` существует только для
`selection_policy` и `ai_provider_settings`. На чистой БД приложение не поднимется: 12 таблиц
схемы Drizzle никто не создаёт.

**178. 🔴 `drizzle.config.json` содержит хардкод-подключение.**
`postgresql://victorkhudyakov@127.0.0.1:5432/crypto_dev` — без пароля, с именем конкретного
пользователя. Не воспроизводится ни на одной другой машине; `DATABASE_URL` из env не используется
конфигом.

**179. 🟠 `timestamp` без таймзоны против `TIMESTAMPTZ`.** Вся схема Drizzle использует
`timestamp(...)` (= `timestamp without time zone`), а raw-SQL в `policy.ts:36-43` и
`settings.ts:133-140` — `TIMESTAMPTZ`. node-postgres парсит naive-timestamp как ЛОКАЛЬНОЕ время
процесса (проверено: парсер типа 1114 интерпретирует строку в TZ процесса), а `defaultNow()`
пишет время сервера БД. При TZ процесса ≠ TZ базы (например, Node в Токио, Postgres в UTC-контейнере)
все смешанные сравнения расходятся на 9 часов. Для системы, где всё строится на `resolveAt`, это
критично. → `timestamp(..., { withTimezone: true })` везде + `TZ=UTC` в окружении.

**180. 🟠 Индексов нет.** В схеме объявлены только primary keys и несколько `unique`
(`assets.symbol`, `combinations.code`, `hypotheses.code`, `learningWeights.categoryName`). Горячие
запросы: `forecasts WHERE status='pending'|'resolved'`, `ORDER BY created_at DESC`,
`candles WHERE symbol=? AND timestamp=?`, `signal_features` — все seq scan.

**181. 🟠 Нет внешних ключей.** `forecasts.hypothesisId` — просто `integer`
(`schema.ts:94`), без ссылки на `hypotheses.id` и без `ON DELETE SET NULL`. TRUNCATE CASCADE в
`/reset` работает только потому, что перечисляет таблицы руками; целостность между таблицами
не защищена.

**182. 🟠 Полные сканы в горячих путях.** `/status` грузит ВСЕ resolved-прогнозы
(`status/route.ts:53-56`) при опросе каждые 20 секунд; `/edge` — все resolved + все hypotheses;
`context.ts:177-180` — все resolved на каждый ИИ-запрос; `loadModelFacts` (`planner.ts:210-220`) —
все resolved без LIMIT. На 100k прогнозов это секунды на запрос и сотни МБ в памяти.

**183. 🟠 `signal_features` и `candles` растут неограниченно.** 15 строк × N активов × 96 циклов/сутки
≈ 15 000 строк в сутки только по сигналам, и никто их не читает. Ретеншена, партиционирования и
архивации нет.

**184. 🟡 `experimentRuns.metricsJson` хранит тяжёлые объекты.** Полный состав вселенной с
обоснованиями, весь planner-decision и массив `assetsInPool` — на каждый цикл
(`autonomous-scheduler.ts:632-660`). JSONB без индекса и без нормализации.

**185. 🟡 `oi_snapshots` — мёртвая таблица.** Объявлена в схеме (`schema.ts:158-167`), не
используется ни одним запросом. Либо заполнять (что дало бы историю OI — см. 40), либо удалить.

**186. 🟡 `assets.isActive` никогда не снимается.** При выходе актива из вселенной флаг остаётся
`true`; реестр растёт, `/status` показывает «все активны» и сортирует по устаревшему `volume24h`.

**187. 🔵 ИДЕЯ: схема под эксперимент, а не под дашборд.**
`cycle_runs(bucket PK)` → `hypotheses(trial_id FK)` → `forecasts(hypothesis_id FK, UNIQUE(hypothesis_id))`
→ `outcomes(forecast_id FK, kind, value, protocol_hash)` + `trials` + `llm_calls` + `feature_snapshots`
с партиционированием по месяцам и materialized views для UI. Плюс pg_partman/архивация.

проведено и сколько осталось в бюджете, когда последний раз трогали holdout, сколько токенов и
денег потрачено, жив ли цикл. Автономная система обязана сама показывать, где её цифры настоящие,
а где нет — иначе доверять её выводам нельзя.

# План работ: четыре фазы

Оценка в человеко-днях (ЧД) при работе одного разработчика с ИИ-помощью. Фазы упорядочены по
принципу «сначала перестать врать себе, потом измерять, потом учиться, потом масштабироваться».

## Фаза 0. Перестать производить ложные данные (3–5 ЧД) — блокирующая

Без этого всё остальное обучение на помойке.

1. Запретить запись синтетики в БД: свечи, тикеры, OI (`isLive: false` → не пишем, помечаем цикл
   как `SKIPPED_NO_DATA`). Находки 21, 22, 23.
2. Отключить авто-seed в UI; seed оставить как отдельный скрипт с явным флагом и колонкой
   `source = 'synthetic'`, исключённой из всех агрегатов. Находки 196, 197.
3. Починить окно разрешения: `[fixedAt, resolveAt]` строго, без «−15 минут», с ценой на `resolveAt`
   из сохранённых свечей. Находки 101, 102, 103.
4. Убрать двойной пересчёт истории в обучении: обучение только по новым исходам, идемпотентно
   (по `forecast_id`, с unique-ключом в `learning_events`). Находки 123, 124.
5. Заменить захардкоженные бенчмарки и `leakageAudit` на реально вычисляемые (baseline =
   случайное направление на тех же бакетах, считаем из `computeMoveStats`). Находки 143, 144, 152.

## Фаза 1. Настоящая автономность (4–6 ЧД)

1. `src/instrumentation.ts` + worker-процесс: единственный серверный триггер, клиентский
   countdown удалить. Находки 1, 2, 3, 4.
2. Цикл по бакетам UTC с unique-ключом и `pg_advisory_lock`; catch-up пропущенных бакетов при
   старте. Находки 5, 6, 7, 19, 20.
3. Транзакция на цикл; изолированный `try/catch` на каждый pick; статус `expired` для просрочки;
   разрешение прогнозов отдельным джобом, не зависящим от скана. Находки 10, 11, 12, 13, 14, 122.
4. Watchdog + алерты (Telegram/webhook) и честный `/api/health`. Находки 20, 194.
5. Ретраи с backoff, rate-limiter на OKX, кэш тикеров в БД. Находки 15, 16, 37.

## Фаза 2. Данные и метки, на которых можно учиться (8–12 ЧД)

1. Бэкап истории: `/market/history-candles` по всей вселенной, unique-индекс
   `(symbol, timeframe, timestamp)`, хранение полных серий (годы 15m — это ~35k строк на актив).
   Находки 29, 30.
2. Хранить снапшоты стакана, фандинга, OI, тикеров. Находка 31.
3. Использовать флаг `confirm` OKX; выровнять `fixedAt` по границе свечи; хранить `bucket`.
   Находки 6, 27, 28.
4. Связать `signal_features` с прогнозом (`forecast_id`) и со временем свечи; это датасет.
   Находка 176.
5. Метка тройного барьера с волатильностным масштабом + три раздельных исхода. Находки 99, 120, 121.
6. Реальные источники вместо прокси: `/market/trades` (CVD), `liquidation-orders`, `rubik/stat/*`,
   `index-tickers` + `mark-price` (базис), `funding-rate-history`. Находки 38–42, 53–56.
7. Point-in-time нормировка всех фич; корреляционный фильтр перед включением в связку.
   Находки 67, 68, 77, 78.

**Результат фазы:** появляется возможность прогнать не 96 экспериментов в сутки, а десятки тысяч
за минуту на истории. Это ключевой рычаг всей затеи.

## Фаза 3. Настоящее обучение и честная статистика (10–15 ЧД)

1. Модель вместо 15 весов: признаки → метка тройного барьера → logistic/GBM, purged k-fold
   с embargo, калибровка изотоникой, важности признаков. Находка 139.
2. Честный Brier по предсказанной вероятности модели (мета-маркировка). Находки 125, 140.
3. Кредит-ассигнация: абляция категорий, взвешивание по уникальности, затухание по времени.
   Находки 126, 131, 149.
4. Реестр испытаний + испытательный бюджет + Deflated Sharpe / PBO при финальной оценке;
   запертый holdout с журналом обращений. Находки 146, 147, 155.
5. A/B-армы отбора (ai / rule / random / momentum) с назначением по ключу бакета. Находки 142, 148.
6. Генерация гипотез моделью через DSL с валидацией и дедупом; EVS заменить на апостериорную
   оценку edge со штрафом за число испытаний. Находки 98, 174, D-раздел.

## Фаза 4. Инфраструктура и эксплуатация (5–8 ЧД)

1. Миграции Drizzle + скрипты `db:generate/push/migrate`, `.env.example`, README, docker-compose
   (postgres + worker + web), бэкапы. Находки 177, 178, 188, 195.
2. Таймзоны: `timestamptz` везде, `TZ=UTC`. Находка 179.
3. Индексы, FK, партиционирование, ретеншен, агрегаты в SQL вместо полных сканов.
   Находки 180–186.
4. Тесты (unit на движке + integration на цикл с подменой источника данных), CI, линт в зелёном.
   Находки 189, 190, 193.
5. Безопасность: аутентификация/авторизация API, allow-list baseUrl провайдеров, секреты вне БД,
   убрать захардкоженные ключи. Находки 156–159.
6. Наблюдаемость: журнал `llm_calls`, стоимость токенов, метрики цикла, экран «Честность данных».
   Находки 160, 165, 175, 200.

# Приложение Б. Проверки, которые выполнить не удалось

- **Прогон приложения end-to-end**: в песочнице нет PostgreSQL, поэтому миграции, реальная
  вставка/чтение, поведение `timestamp` при несовпадающих TZ и фактические тайминги цикла
  проверены только чтением кода и локальным тестом парсера типов `pg` (179).
- **Реальные ответы OKX**: сеть ограничена allow-list'ом (okx.com недоступен), поэтому формат
  ответа `/market/candles` с полем `confirm` (27), лимиты и доступность `rubik/stat/*`,
  `market/trades`, `public/liquidation-orders` (38–42) нужно сверить с документацией биржи
  перед реализацией.
- **Фактические задержки LLM-провайдеров**: ключей нет, константы `PLANNER_DEADLINE_MS = 40000`
  и `PLANNER_MAX_TOKENS = 700` (164, 163) проверены только по комментариям в коде.
